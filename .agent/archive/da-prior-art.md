## R1

**Surface + referent semantics.** Official [ACE interpretation rules](https://attempto.ifi.uzh.ch/site/docs/ace_interpretationrules.html): “Arithmetic expressions are built from numbers, variables and proper names with the help of the operators +, -, \*, /, ^.” / “Arithmetic operators have types, meaning that all arguments must eventually stand for numbers.” / “Note: The ACE parser APE does not evaluate expressions.” [Construction rules](https://attempto.ifi.uzh.ch/site/docs/ace_constructionrules.html): “Boolean formulas also count as sentences.” / “The ACE parser APE does not evaluate boolean formulas.”

Local grammar `vendor/ape/prolog/parser/grammar.fit:1620–1643` records `drs!out!drs(Dom, [formula(X, '=', Y)-ID/TID | Conds])` with the two terms' `sem!expr!X` / `sem!expr!Y`. Lines 5722–5746 use `word_noninitial(Op, (Op == '*' ; Op == '/'))` and `sem!exprpart!expr(Op, X, Y)`. Lines 6025–6031: `atomic_term(AVM & sem!expr!X) --> variable_np(AVM & sem!index!X).` Thus **inference**: formula operands reuse referents; treating a plural referent as its cardinality requires an additional semantic rule, not merely accepting `formula/3`.

**RACE.** Norbert E. Fuchs, “Reasoning in Attempto Controlled English: Mathematical and Functional Extensions,” [CNL 2021 proceedings](https://aclanthology.org/2021.cnl-1.pdf), printed pp. 61–65. Page 62: “the evaluation of expressions – as in A is B + C. C is D - 1. B is 2. D is 3. – must be delayed until all constituents have a value.” / “RACE uses SWI Prolog's library clpqr … that provides constraint logic programming over rationals and reals, and also logical entailment.” Page 63 shows `The capital C is 1000.00.`, `The interest I is 0.005.`, and a formula using C/I. It also shows `A farmer has a number X of some cows and has a number Y of some ducks.`, followed by `X+Y=100.` and `4*X+2*Y=260.` This numeric-*attribute* idiom is evidence against silently identifying an ordinary plural-group referent with its cardinality.

**Official DRS examples.** [DRS report 6.6](https://attempto.ifi.uzh.ch/site/pubs/papers/drs_report_66.pdf), §3.6: `A number is 14.` → `object(A,number,countable,na,eq,1)` + `predicate(B,be,A,int(14))`; `A value is (1 + 2) / X * 4.` → `predicate(C,be,A,expr(*,expr(/,expr(+,int(1),int(2)),B),int(4)))`. §3.9: `John’s weight is 80 kg.` → `predicate(B,be,A,int(80,kg))`. These establish `int/1` = integer literal, `real/1` = real-valued numeric literal, `int/2` = numeric literal + measurement-unit symbol, `expr/3` = expression tree; the numeric value is related to the NP referent by the copula, not its `object/6` cardinality. §7.5: `X >= 13.4.` → `object(A,something,dom,na,na,na)` + `formula(A,>=,real(13.4))`. The report's first §7.5 example mismatches `10 = 4 + 6.` with `formula(int(5),=,int(3))`; that apparent editorial error is not used as evidence.

**APE exporters.** [Upstream FOL converter](https://raw.githubusercontent.com/Attempto/APE/master/prolog/utils/drs_to_fol_to_prenex.pl), lines 223–225: `cond_to_fol(BasicCondition - Index, World, NewBasicCondition - Index) :- BasicCondition =.. [Functor|Arguments], NewBasicCondition =..[Functor|[World|Arguments]].` It preserves an ordinary `formula` predicate with a world argument; it does not evaluate arithmetic. [TPTP converter](https://raw.githubusercontent.com/Attempto/APE/master/prolog/utils/drs_to_tptp.pl), lines 169–174: `cond_to_tptp(formula(R1, Symbol, R2), Pred)` transforms operands and constructs `Pred =.. [Symbol, NR1, NR2]`; lines 242–264 keep variables as variables, unwrap `int(Arg)` / `real(Arg)`, and preserve `int(Arg, Unit)` / `real(Arg, Unit)`; lines 278–283 rebuild an expression as `Expr =.. [Op, NArg1, NArg2]`. **Inference:** these converters do not introduce a group-cardinality→scalar coercion; downstream numeric interpretation is not provided by accepting the formula alone.

**Exact-decimal input hazard.** `vendor/ape/prolog/parser/tokenizer.pl:165–170`: `get_number(Cs, Prefix, Remaining), number_codes(Number, [C | Prefix]), get_atomics(Remaining, Ts).` Grammar `grammar.fit:6082–6090` stores `sem!expr!real(Real)` and consumes `word(Real, ( number(Real), \+ integer(Real) ))`. Measured under the project shim: `number_codes(A,"0.1"), number_codes(B,"0.10000000000000000000000001")` prints `values(0.1,0.1)`, `same_term`, `float`; rc=0. Therefore a canonical exact-decimal KB term alone cannot recover all literal digits from existing DRS float terms; preserve/reparse the source lexeme or extend the tokenizer. This is a local measurement + inference, not a claim that the proposed factors themselves exceed float display precision.

**AceRules / ACE View: none-found for automatic plural-referent arithmetic.** Searched the [AceRules webservice specification](https://attempto.ifi.uzh.ch/site/docs/acerules_webservice.html), [ACE-to-OWL guide](https://attempto.ifi.uzh.ch/site/docs/writing_owl_in_ace.html), [upstream OWL/SWRL converter](https://raw.githubusercontent.com/Attempto/APE/master/prolog/utils/owlswrl/drs_to_owlswrl_core.pl), and targeted `AceRules arithmetic numbers` / `AceView arithmetic formula` web queries. The OWL guide explicitly says “Not all ACE constructions map nicely to OWL. Therefore, we describe only a subset of ACE.” For numeric data properties it prescribes “the copula verb”, a genitive/of construction, “a noun which expresses the property, and finally a number or a string”, e.g. `Everybody whose age is 32 is a grown-up.` That is numeric-attribute evidence, not support for general `formula` execution on a plural referent. The webservice docs do not settle an arithmetic subset; no live AceRules/ACE View conformance probe was run. Do not generalize RACE's CLP(Q/R) extension to every ACE tool.

## R2

**Countable plural.** `vendor/ape/prolog/parser/grammar_functionwords.fit:788–808`:

```prolog
%% existential quantifier (plural)
exists_pl_avm :=
    ...
    sem!index!X &
    sem!quantity!number!2 &
    sem!quantity!comparison!geq.

determiner(
    @exists_pl_avm &
    display!tree![det,some] &
    syn!head!agr!num!<pl
) -->
    word_capitalize(some, 'Some').
```

Ellipsis removes unrelated feature assignments; displayed assignments are verbatim. Lines 810–815 instead select `@exists_sg_avm` and `syn!head!agr!num!<mass` for mass-noun `some`.

**Official report confirms the lower bound.** [DRS report 6.6](https://attempto.ifi.uzh.ch/site/pubs/papers/drs_report_66.pdf), §3.4, printed p. 17: `some cards` → `object(A,card,countable,na,geq,2)`. §3.9 separately gives `2 kg of apples` → `object(A,apple,countable,kg,eq,2)` and `2 kg of rice` → `object(A,rice,mass,kg,eq,2)`.

**Measurement phrase ≠ countable plural.** [ACE construction rules](https://attempto.ifi.uzh.ch/site/docs/ace_constructionrules.html): “Measurement noun phrases are built from numbers followed by measurement nouns and optionally followed by *of* and a bare mass noun or a bare plural noun.” Examples: `2 m`, `1.4 l of water`, `3 kg of apples`. It separately lists `some cards` under “Plural countable common noun phrases can be collective” and `some water` as a mass-noun phrase. [Interpretation rules](https://attempto.ifi.uzh.ch/site/docs/ace_interpretationrules.html): “By default, plural noun phrases have a collective reading; distributive reading is indicated by *each of*.”

**Implication (inference):** `some MME-units-per-day Y`, if lexicon-classified as countable plural, asserts a collection of at least two; it is not an unconstrained scalar. Supporting fractional or sub-two outputs must use another carrier or explicitly revise this semantics. Mass-noun authoring avoids plural lower bound but does not by itself make the referent numeric. **none-found** for a tool-wide alternative that turns countable `some <unit plural>` into an unconstrained amount; places searched = R1's official rules/report, RACE paper, exporters, AceRules webservice and OWL/ACE guide. Mass nouns and measurement-unit literals are separate supported representations, not an alternate interpretation of the same countable-plural parse.

## R3

- **Logical English.** [Official README](https://raw.githubusercontent.com/LogicalContracts/LogicalEnglish/master/README.md): “New translation of is in English as unification \"=\" in Prolog.” / “New translation of = in English as \"is\" assignment in Prolog.” [Syntax](https://raw.githubusercontent.com/LogicalContracts/LogicalEnglish/master/le_syntax.md) gives `a number X is greater than a number Y if` / `X > Y.` The cited prose does not promise decimal arithmetic or automatic unit conversion; LE2's current reference below documents its expression syntax separately.
- **PENG-ASP.** Schwitter & Guy, “Answer Set Programming for Controlled Natural Language Processing,” [NLPAR 2015 proceedings](https://peterschueller.com/pub/2015/nlpar2015-proceedings.pdf), printed p. 23, §7.2: “PENGASP allows us to specify arithmetic operations in the antecedent of conditional sentences and in imperative sentences (constraints). Example: “If there is an office N1 and there is an office N2 and N2 is equal to N1 plus 1 then the office N2 is right of the office N1.” This establishes symbolic numeric variables + verbal arithmetic; multiplication, decimal/percentage/unit semantics are not specified in that section.
- **RuleSpeak/SBVR.** [“The RuleSpeak Business Rule Notation,” Ronald G. In these forms, 'always' is assumed implicit.” The table lists “is to be computed as” / “for computation” and “is to be fixed at [number]” / “for establishing constants”. - **GF-based CNL, not a shared numeric semantic standard.** Kaarel Kaljurand's [CNL 2012 talk](https://kaljurand.github.io/Grammars/files/cnl2012_speech_slides/index.html) gives `Expr | arithmetical expressions, e.g. (((1 + -2.3) * PI) ^ 5)` and `Unitconv | unit and currency conversion expressions, e.g. convert 12.34 km^2 to ft^2`. It states “type-aware unit conversion expressions” and illustrates a rejected type mismatch: `syntax error: "convert 10 USD to km/h"`. - **Attempto-derived clinical CNL: none-found for executable arithmetic policy.** Searched Shiffman et al., [“Writing Clinical Practice Guidelines in Controlled Natural Language”](https://attempto.ifi.uzh.ch/site/pubs/papers/cnl2009main_shiffman.pdf), full extracted text + its recommendation appendix. - **Logical English 2 arithmetic.** [Official language reference §7](https://raw.githubusercontent.com/LogicalContracts/LogicalEnglish2/main/docs/user/reference/language.md): `+`, `-`, `*`, `/`, `( )`, integer division `//`, remainder `mod`; example `ENT = ETI * ATR - TO`. “Prolog calculates them with `is/2` while the query runs.” “When one side has no value yet, `=` gives it the value of the other side, as in `R = N mod 3`.” It explicitly describes fixed-point application code: “Contract code that keeps a fixed number of decimals uses this arithmetic.” This is an integer-scaling *authoring pattern*, not a universal exact-decimal LE numeric type. §2.2 says “arithmetic cannot operate on a name”; obtain its value first. §2.3 repeats “Put the value into a variable first, then do the arithmetic.” This is useful prior art for separating a dosage entity from its numeric value.
- **none-found / bounded gaps:** PENG multiplication spelling, decimal/percentage/unit-conversion policies beyond §7.2; a fixed numeric type in RuleSpeak; exact evaluator/rounding policy behind GF Unitconv. Searched the cited primary docs + three targeted CNL web queries and one GF query. These gaps are not evidence that the languages cannot express those operations.

## R4

**SWRL relation ≠ a universal binding algorithm.** [W3C SWRL submission §8.2](https://www.w3.org/submissions/SWRL/): `swrlb:multiply` is “Satisfied iff the first argument is equal to the arithmetic product of the second argument through the last argument.” The numeric built-ins' precondition is “the arguments all have to belong to some numeric type for which the relation is defined.” Thus result-first syntax is primary-source-supported, but operational treatment of missing inputs requires an engine-specific check. SWRL's own introduction warns “OWL DL becomes undecidable when extended in this way”. Read via Neo after webtext returned HTTP 403. [SWRLAPI implementation](https://raw.githubusercontent.com/protegeproject/swrlapi/master/src/main/java/org/swrlapi/builtins/swrlb/SWRLBuiltInLibraryImpl.java), lines 334–338, routes `multiply` to `mathOperation`. Lines 1477–1502: `checkForUnboundNonFirstArguments(arguments); // Only supports binding of first argument`; multiplication starts `operationResult = BigDecimal.ONE;` and accumulates `operationResult.multiply(getArgumentAsADecimal(argumentNumber, arguments))`. Lines 1561–1571 bind the first argument with `arguments.get(0).asVariable().setBuiltInResult(resultArgument)` when unbound; otherwise compare it to the computed value. **Conclusion:** this implementation supports result-first binding with bound inputs, not arbitrary inverse solving; missing non-first bindings enter its unbound-argument check. This is source inspection, not a runtime conformance test or an assurance claim about every SWRL engine.

**RIF function + domain guard.** [RIF Datatypes and Built-Ins §4.5.1](https://www.w3.org/TR/rif-dtb/): numeric multiplication is a binary function with schema `(?arg1 ?arg2; func:numeric-multiply( ?arg1 ?arg2) )`. The declared domains include value spaces `xs:integer`, `xs:double`, `xs:float`, `xs:decimal`, with XPath numeric promotion and domain restrictions. The general built-in semantics says: “When an argument falls outside of its domain, it is understood as an error.” “This means that if one or more of the arguments is not in its domain, the value of Iexternal(σ)(a1 ... an) is unspecified.” “the only safe way to communicate rule sets that contain built-ins among RIF-compliant systems is to use datatype guards.” Therefore wrong-type behavior needs a project contract; the RIF spec is not an exact-decimal-only guarantee. Read via Neo after webtext HTTP 403.

**Soufflé distinguishes grounding from termination.** [Official tutorial](https://souffle-lang.github.io/tutorial): “Variables in functors must be grounded for use. That is, they may not contain any free variables.” But also: “For practical usage, Soufflé extends Datalog to make it Turing-equivalent through arithmetic functors.” / “This results in the ability of the programmer to write programs that may never terminate.” Its explicit example is `A(0).` plus `A(i + 1) :- A(i).`; the constrained example is `A(x+1) :- A(x), x < 9.` **Conclusion:** safety/range restriction supplies usable input bindings; it does not bound recursive numeric generation.

**Clingo grounding.** [Potassco guide source](https://raw.githubusercontent.com/potassco/guide/master/language.tex), lines 299–308: “rules are required to be … safe” and “all variables in a rule must occur in some positive literal … in the body of the rule.” Lines 520–524: arithmetic functions “are evaluated during grounding”; the basic arithmetic terms are integers. Lines 559–567 qualify safety: only simple arithmetic terms with exactly one variable occurrence count as positive; a multiplication's constant part must not evaluate to zero. Lines 631–654 explain equality can define a shorthand; inputs X/Y come from `num/1`, and equalities derive XX/YY/Y′. This is a restricted binding mechanism, not general equation solving over decimal uncertainty.

**Design inference.** For the proposed multiplication-only KB: an arithmetic literal should have a declared direction; input values ground, numeric and unit-compatible before evaluation; result either bound once or checked against an existing value; no inverse guessing of operands. Acyclic dependencies from finite EDB inputs, or another explicit finite-domain/termination argument, are additionally needed if arithmetic can create new head values recursively. Existing depth/inference limits can bound execution, but a limit trip is not a proof of falsehood or a proof that arithmetic rules terminate.

## R5

**Reference implementation.** [OMTKLogic 3.0.0](https://fhir.org/guides/cdc/opioid-mme-r4/Library-OMTKLogic.html) declares `library OMTKLogic version '3.0.0'`. `GetDailyDose(..., dosesPerDay Decimal)` branches:

- Mass input: `when doseQuantity.unit in { 'mg', 'ug' } then` → `Quantity { value: dosesPerDay * doseQuantity.value, unit: doseQuantity.unit }`.
- Volume input: `when doseQuantity.unit = 'mL' and (PositionOf('/mL', strength.unit) = Length(strength.unit) - 3) then` → `Quantity { value: dosesPerDay * doseQuantity.value * strength.value, unit: StripPer(strength.unit) }`.
- Other unit-count input: comment `/* if doseQuantity is not in actual units (e.g., 1 tab, 1 spray -- when it's a combo med with a unit of tablet, or it's mg/actuat) -->  daily dose = numTimesPerDay * dose value * strength value */`; corresponding expression again `dosesPerDay * doseQuantity.value * strength.value`.
- Patch: `when ToInteger(doseFormCode.code) = 316987 then` and `if ToInteger(ingredientCode.code) in { 1819, 4337 } then` → `Quantity { value: dosesPerDay * doseQuantity.value * strength.value, unit: strength.unit }`.
- Missing inputs: `when dosesPerDay is null or doseQuantity is null or strength is null or strength.value is null or strength.unit is null then` → `result: null as Quantity`.

`CalculateMMEs` obtains `Ingredients: GetIngredients(M.rxNormCode)`, then `factor: ConversionFactors.GetConversionFactor(I.ingredientCode, dailyDose.result, I.doseFormCode, M.dosesPerDay)` and `mme: Quantity( Round(dailyDose.result.value * factor, 1), '{MME}/d' )`. **Conclusion:** rounding occurs per ingredient, before aggregation; this is an implementation choice, not evidence that the source guideline asks for rounding.

[MMECalculator 3.0.0](https://fhir.org/guides/cdc/opioid-mme-r4/Library-MMECalculator.html): per-prescription `mme: Sum(mmePerIngredient X return X.mme)`; `TotalMME` returns `OMTKLogic.Quantity( Sum((MME(prescriptions)) M return M.mme.value), '{MME}/d' )`. Its comment states: “The calculation assumes the most aggressive dosing, and is performed for all medications in the given list (i.e. no additional filtering for status is performed).”

**Do not import old defaults as CDC 2022.** [ConversionFactors 3.0.0](https://fhir.org/guides/cdc/opioid-mme-r4/Library-ConversionFactors.html) uses `Coalesce( LookupConversionFactor(ingredientCode, dailyDose, doseFormCode, dosesPerDay), case ToInteger(ingredientCode.code) ... )`. The fallback includes `when 2670 then 0.15 /* Codeine */`, `when 5489 then 1 /* Hydrocodone */`, `when 3423 then 4 /* Hydromorphone */`, `when 7052 then 1 /* Morphine */`, `when 7804 then 1.5 /* Oxycodone */`, `when 7814 then 3 /* Oxymorphone */`. For methadone (`when 6813`), verbatim branch conditions/results: `when dailyDose.value between 1 and 20 then 4`, `when dailyDose.value between 21 and 40 then 8`, `when dailyDose.value between 41 and 60 then 10`, `when dailyDose.value >= 61 then 12`. Fentanyl patch fallback is `(0.33333333 / dosesPerDay) * 7200`, not a naked 2.4; its surrounding normalization must be retained before interpreting that number. Unlisted ingredients fall into `UnknownIngredientCode`. A supplement can override all of this: “If neither of these configurations is available, the hard-coded conversion factors in GetConversionFactor will be used.”

[Published 2022.1.1 IG](https://fhir.org/guides/cdc/opioid-cds/2022.1.1/) says “All doses are in mg/day except for fentanyl, which is mcg/hr.” It separately cautions “Equianalgesic dose conversions are only estimates and cannot account for individual variability in genetics and pharmacokinetics.” and “Do not use the calculated dose in MMEs to determine the doses to use when converting one opioid to another”. ## R6

**FHIR R5 numeric representation.** [Datatypes](https://hl7.org/fhir/R5/datatypes.html): decimal = “Rational numbers that have a decimal representation. Decimals in FHIR cannot have more than 18 digits and a decimal point.” Precision text: “e.g. 0.010 is regarded as different to 0.01, and the original precision should be preserved”; “Implementations SHALL handle decimal values in ways that preserve and respect the precision of the value as represented for presentation purposes.” Crucial qualifier: “Implementations are not required to perform calculations with these numbers differently, though they may choose to do so (i.e. preserve significance).” Candidate implementations explicitly include “GMP implementations or equivalents to Java BigDecimal that implement arbitrary precision, or a combination of a (64 bit) floating point value with a precision field.” **Conclusion:** FHIR presentation fidelity supports keeping a lexical scale separately; it does not require the KB to adopt arbitrary precision or forbid every internal float implementation. A normalized `decimal(10,2)`→`decimal(1,1)` loses original significance unless custody/display retains it elsewhere.

**FHIR comparator is semantic.** Same source: “If no comparator is specified, the value is a point value (i.e. '='). The `comparator` element can never be ignored.” [FHIRHelpers](https://hl7.org/fhir/uv/cql/Library-FHIRHelpers.html), library declaration `library FHIRHelpers version '4.0.1'`:

```cql
when quantity.comparator is not null then
    Message(null, true, 'FHIRHelpers.ToQuantity.ComparatorQuantityNotSupported', 'Error', 'FHIR Quantity value has a comparator and cannot be converted to a System.Quantity value.')
```

`ToQuantityIgnoringComparator` is documented: “This function should only be used when an application is justified in ignoring the comparator value (i.e. the context is looking for boundary).” `ToInterval(quantity FHIR.Quantity)` handles `'>='` by `Interval[ ToQuantityIgnoringComparator(quantity), null ]`, `'>'` by `Interval( ToQuantityIgnoringComparator(quantity), null ]`, and absent comparator by `Interval[ToQuantity(quantity), ToQuantity(quantity)]`. **Inference:** `>=60 mg` is a set/range, not a dose known to equal 60 mg. Multiplication by a known positive 1.5 maps the lower-bound set to `>=90` in the corresponding output unit, not exactly 90. Standards do not authorize the latter endpoint substitution. If cnl-ckc implements scalar multiplication only, reject/defer non-singleton operands rather than silently dropping their comparator. Zero/negative multipliers, two uncertain operands, unit validity and open endpoints need their own interval contract if offered; this survey did not find a CQL interval-multiplication overload that automatically supplies it.

**CQL version distinction.** [Current published reference](https://cql.hl7.org/09-b-cqlreference.html) identifies itself as “v2.0.0: R2 STU 1”. It says “implementations must support at least the 28 digits of precision and 8 digits of scale, but may support more precise values.” The Decimal description defines precision as “total number of possible digits” and scale as “number of possible digits to the right of the decimal”. This is a finite decimal baseline, not a requirement for unbounded rationals. `/` is “Decimal division; for Integer division, use the truncated divide (div) operator.” “If the result of the division cannot be represented, or the right argument is 0, the result is null.” `Round` is explicit: “a decimal value greater than or equal to 0.5 and less than 1.0 will round to 1, and a decimal value less than or equal to -0.5 and greater than -1.0 will round to -1.” “Precision determines the decimal place at which the rounding will occur.” This is half-away-from-zero, not bankers' rounding. The attempted version path `https://cql.hl7.org/1.5.3/09-b-cqlreference.html` returned 404; current-version claims above are not silently attributed to 1.5.3. Historical CQL 1.5.3 policy was not checked; the row's numeric guarantees explicitly concern current CQL 2.0.0.

**UCUM = unit algebra, not a decimal storage format.** [UCUM specification](https://ucum.org/ucum), §16: “defined by the algebraic operations of multiplication, division and exponentiation between units, by the equivalence relations of equality and commensurability of units, and by the multiplication of a unit with a scalar.” §18.5: “The product u′ = ru of a real number scalar with the unit u is also a unit”. §20.2 represents a unit as a pair of magnitude + dimension vector. §21 distinguishes non-ratio “special units”, for which conversion uses mutually inverse real functions. [CQL Multiply](https://cql.hl7.org/09-b-cqlreference.html#multiply): “For multiplication involving quantities, the resulting quantity will have an appropriate unit as determined by application of the UCUM specification.” Its examples `12 'cm' * 3 'cm'` and `3 'cm' * 12 'cm2'` yield `cm2` and `cm3`; “Attempting to operate on quantities with invalid or special units will result in null.” **Conclusion:** a small audited exact-decimal subset of dose-unit conversions is a legitimate scoped design; claiming full UCUM support would be substantially broader. No comparator-product or universal exact-decimal implementation law was found in the examined UCUM semantic sections.

## R7

**SWI exact rational path.** [Official manual, Rational numbers or floats](https://www.swi-prolog.org/pldoc/man?section=rational-or-float): “SWI-Prolog uses rational number arithmetic if the Prolog flag prefer_rationals is true and if this is defined for a function on the given operands. This results in perfectly precise answers.” The same paragraph warns “rational numbers can get really large” and names `max_rational_size` as a tripwire. “Floating point arithmetic can be forced by forcing a float into an argument at any point, i.e., the result of a function with at least one float is always float except for the float-to-integer rounding and truncating functions”. Therefore `prefer_rationals` alone does not repair APE's pre-parsed decimal floats.

**SWI rational syntax is an extension, not universal ISO interchange.** [Official rational syntax manual](https://www.swi-prolog.org/pldoc/man?section=syntax-rational-numbers): “there are few options for adding rational numbers without breaking the ISO standard.” “ECLiPSe and SWI-Prolog have agreed to define the canonical syntax for rational numbers to be e.g., `1r3`.” It also documents `1_3` for ECLiPSe, configurable `1/3` in SWI, and `write_canonical/1` always using `1r3`. [Arithmetic manual](https://www.swi-prolog.org/man/arith.html): rational numbers are “always kept in canonical representation, which means M is positive and N and M have no common divisors”; support depends on GMP, and ordinary floats use C `double`. “The use of rational numbers with unbounded integers allows for exact integer or fixed point arithmetic under addition, subtraction, multiplication, division and exponentiation”. **Conclusion:** exact arithmetic exists in mature Prolog systems, but `1r3` and its evaluation flags are not a portable all-engine contract.

**Scaled-integer precedent.** LE2's official arithmetic reference (R3) explicitly says “Contract code that keeps a fixed number of decimals uses this arithmetic.” This supports application-specified scaling using integer operations; it does not define a standard Prolog `decimal/2` type.

**Native exact-decimal precedent, but nonstandard.** [Amzi! Prolog “Numbers and Math”](https://www.amzi.com/manuals/amzi/pro/ref_math.htm), read through Neo after HTTP 403 from webtext, distinguishes `Real(fixed)` and `Real(long)` from floats; its type-test example is `numeric_type(3.3r, T).` → `T = fixed_real ; T = real ;`. It explicitly says “Real numbers are kept in a non-standard floating point format with a mantissa and exponent.” and “A real number is said to be normalized if there are no leading zeros and no trailing zeros in the mantissa, unless the real number is actually zero. The result of any real arithmetic operation is normalized.” This is an existing decimal-oriented Prolog implementation, not a shared portable `decimal/2` term convention. The manual's generic “infinite precision” wording is not treated as a literal unlimited-resource guarantee.

**none-found / bounded search:** a portable standardized `decimal(Mantissa,Scale)` numeric term. Places searched = official SWI arithmetic + rational syntax, Amzi number manual, [ECLiPSe floating-point standardization proposal](https://eclipseclp.org/Specs/core_update_float.html), LE2 arithmetic reference, and queries `Prolog exact decimal arithmetic "decimal" "scale" library`, `SWI Prolog rationals prefer_rationals 1r3 ISO portability decimal`, `Prolog "decimal(" "mantissa" scale`. A Jekejeke BigDecimal manual mirror was only a lead, not relied on. GNU Prolog's official manual at both HTTPS hostnames failed TLS hostname validation (rc=1); no claim rests on it. No standalone ISO standard text or exhaustive Prolog-package census was read. Thus the report does not upgrade a bounded search into a proof of ecosystem-wide absence.

**Design inference.** A compound such as `decimal(15,1)` is portable *term data* within target engines' integer limits; no found standard makes `is/2`, numeric comparison, or a generic consumer assign it scaled-integer numeric semantics automatically. Publish the interpretation, canonicalization, input/result modes, integer/scale bounds and overflow behavior with the schema's arithmetic predicates. For `value = M × 10^(-S)`, finite-decimal multiplication is closed: `(M1,S1) × (M2,S2) = (M1×M2,S1+S2)` before canonicalization; division is not generally closed (one third). This is an elementary derivation, not an externally sourced library claim. It supports the proposed multiplication-only exact-decimal design, without importing SWI rationals or pretending the term is an ISO number.
