## Detail sections (keyed by row id; evidence + excerpts)

### V1 — clinical behavior matters beyond syntax

- CPG STU2 delegates library guidance: https://hl7.org/fhir/uv/cpg/STU2/libraries.html — “Computable content using CQL SHALL conform to the profiles defined in the Using CQL With FHIR IG”.
- CQL: https://hl7.org/fhir/uv/cql/using-cql.html — “When an artifact moves to active status, a version is required in either the CQL source, the translated ELM (if included), or the containing FHIR Library resources.” Three change classes: “A library can be changed in a way that would alter the public use of its components.” / “A library can be changed by adding new components or functionality but without changing the way that existing components are used.” / “A library can be changed in a way that does not change existing components or add new components, but only corrects or improves the originally intended functionality.”
- CRMI STU2: https://hl7.org/fhir/uv/crmi/STU2/en/artifact-lifecycle.html — “non-breaking changes or minor new capabilities (such as refining the content of a questionnaire or adding stratifiers to a quality measure) require a minor version number increment; while non-substantive changes (such as fixing spelling mistakes and other minor technical corrections) require only a patch version number increment.”
- Inference: cnl-ckc must declare whether release compatibility means parser/schema compatibility, stable clinical query behavior, or both. Calling a clinically substantive correction PATCH merely because predicates remain unchanged follows neither the stronger CRMI wording nor an explicit stable-answer contract.

### V2 — separate version axes; collection versions can avoid per-document churn

- FHIR R4: https://hl7.org/fhir/R4/library-definitions.html — Library.version: “This is a business versionId, not a resource version id”; “The version can be appended to the url in a reference to allow a reference to a particular business version of the library with the format [url]|[version].”
- CQL dependency representation: https://hl7.org/fhir/uv/cql/conformance.html — “Data Model (using declaration)” maps to “`depends-on` with `url` of the ModelInfo Library (e.g. `http://hl7.org/fhir/Library/FHIR-ModelInfo\|4.0.1`)”. This is distinct from the logic-library version. The same page says “The version of CQL/ELM used for content in a library **SHOULD** be specified using the version parameter of the text/cql and application/elm+xml, application/elm+json media types.”
- FHIR target pin: https://hl7.org/fhir/R4/implementationguide-definitions.html — ImplementationGuide.fhirVersion: “The version(s) of the FHIR specification that this ImplementationGuide targets - e.g. describes how to use.” Dependency version: “The version of the IG that is depended on, when the correct version is required to understand the IG correctly.”
- CRMI collection policy: https://hl7.org/fhir/uv/crmi/STU2/en/artifact-lifecycle.html — “The version of the artifact is dictated by the version of the package in which the artifact is published. Note in particular this means that changes in the version do not necessarily imply changes in the content of the artifact.” / “Artifact collections **SHOULD** use an Artifact Manifest to establish versions of dependencies”.
- Inference: one release manifest can pin per-guideline inputs/digests without introducing a version number on every ACE document. No standard inspected requires all historical releases to be recompiled after a new schema release.

### V3 — dataset conventions are choices, not clinical guarantees

- Frictionless: https://datapackage.org/recipes/data-package-version/ — MAJOR examples: “Change a field `type` or `format`”; “Combine, split, delete or change the meaning of data that is referenced by another data resource”. MINOR: “Add new data to an existing data resource”. PATCH: “Correct errors in existing data”. First publication scenario: “You release your data for the first time. Use version 1.0.0”.
- DCAT §11 (non-normative): https://www.w3.org/TR/vocab-dcat-3/ — “The notion of version is very much related to the community practices, the data management policy and the workflows in place. It is up to data providers to decide when and why a new version should be released. For this reason, DCAT refrains from providing definitions or rules about when changes in a resource should turn into a new release of it”. Relationships: “Property dcat:previousVersion is used to build a version chain that can be navigated backward from a given version to the first one.” / “property dcat:hasVersion can be used to specify a version hierarchy, by linking an abstract resource to its versions.”
- schema.org: https://schema.org/version — “The version of the CreativeWork embodied by a specified resource.” No bump algorithm found on this property page.
- SemVer: https://semver.org/spec/v2.0.0.html — “Once a versioned package has been released, the contents of that version MUST NOT be modified. Any modifications MUST be released as a new version.” / “Build metadata MUST be ignored when determining version precedence.” Consequently, a changed `+g<sha>` suffix alone does not increase SemVer precedence. Recommendation: bump the public KB version for a content upgrade rather than relying only on that suffix.

### V4 — provenance fields and their distinct jobs

**Source requirements:**

- BagIt RFC 8493: https://www.rfc-editor.org/rfc/rfc8493.html — “Every payload manifest MUST list every payload file name exactly once.” `BagIt-Version` identifies the BagIt format, not the KB schema or release: “M.N identifies the BagIt major (M) and minor (N) version numbers.” Reserved optional metadata: “Source-Organization: Organization transferring the content.”; “External-Description: A brief explanation of the contents and provenance.”; “Bagging-Date: Date (YYYY-MM-DD) that the content was prepared for transfer.”; “External-Identifier: A sender-supplied identifier for the bag.”; “In addition to these metadata elements, other arbitrary metadata elements MAY also be present.”
- RO-Crate: https://www.researchobject.org/ro-crate/specification/1.2/root-data-entity.html — “The *Root Data Entity* MUST have all of the properties listed below.” List: `@type`, `@id`, `name`, `description`, `datePublished`, `license`; `@type` “MUST be Dataset or an array that contains `Dataset`”. Caveat: “The properties above are not sufficient to generate a DataCite citation.”
- RO software provenance: https://www.researchobject.org/ro-crate/specification/1.2/provenance.html — “the software application SHOULD be represented with an entity of type SoftwareApplication, with a version property”; “The software SHOULD be associated with the File(s) (or other data entities) it created as an instrument of a CreateAction, with the File referenced by a result property. Any input files SHOULD be referenced by the object property.”
- PROV-O: https://www.w3.org/TR/prov-o/ — “A derivation is a transformation of one entity into another.” / “An Agent's responsibility for an Activity or Entity is described using the properties prov:wasAssociatedWith and prov:wasAttributedTo, respectively.” A vocabulary, not an archive's mandatory field checklist.
- CFF schema guide: https://raw.githubusercontent.com/citation-file-format/citation-file-format/main/schema-guide.md — required top-level fields `authors`, `cff-version`, `message`, `title` each carry “**required**: `true`”. `cff-version`: “The Citation File Format schema version that the `CITATION.cff` file adheres to for providing the citation metadata.” `version`: “The version of the software or dataset.” `commit`: “The commit hash or revision number of the software version.” `date-released`: “The date the software or data set has been released.” CFF does not replace compiler/review custody evidence.

**Recommended cnl-ckc release record — synthesis, not a claim of compliance:**

| field group | proposed contents | basis |
|---|---|---|
| Identity/citation | release ID, release date, title, creators/ORCIDs, publisher/contact, license, version DOI, concept DOI, repository + full Git commit | BagIt external identifier/date/contact; RO-Crate root; CFF; V5 |
| Contract | exact schema version/ID + schema artifact digest; precise compatibility declaration; compiler version + full commit; pinned toolchain/dependency manifest digest | separate model/content axes V2; versioned software/input/result links above |
| Sources | guideline ID + source edition/date + canonical URL/DOI + source-byte digest; relevant document/region identifiers | source identity V6; PROV derivation; RO input links |
| Custody/results | ACE/Prolog/review/export manifest digests and existing proof/query evidence references; archive SHA-256 in an external release record | existing project custody requirement supplied in brief; BagIt manifests; PROV input/output links |
| Evolution | predecessor release DOI/ID; changed guidelines/documents; change class separating schema compatibility from clinically substantive changes; paper arXiv URL/version | DCAT chain V3; CRMI V1; Zenodo V5 |

The archive's own SHA-256 belongs outside that archive to avoid a self-reference. Reuse existing custody manifests; these standards do not justify duplicating every digest into several independent authoritative records. RO-Crate is an optional interoperable representation of the record, not a prerequisite for a sound release policy.

### V5 — publish the KB product, not accidentally only its repository

- https://zenodo.org/help/versioning — “When you publish an upload for the first time, we register two DOIs”; “Afterwards, we register a DOI for every new version of your upload.” / “You should only create a new version if you want to update the files of your record.” Metadata can change without a new DOI, so a DOI pins files more strongly than mutable descriptive metadata.
- GitHub integration workflow: https://help.zenodo.org/docs/github/archive-software/github-upload/ — “Create a release in GitHub.” / “Wait for the release to be processed.” / “When the release is finished, click the record DOI to go to the record”. These instructions do not establish that attached BagIt assets are archived.
- Asset uncertainty: https://github.com/zenodo/zenodo/issues/1235 — issue description: “Since the zipball of the source code is already downloaded, it might be also worth looking at downloading and including the assets in the produced record.” Current end-to-end behavior **not confirmed**; inspected current archiving docs + this issue, did not create a test release. Recommendation: explicitly upload the deterministic KB tarball and verify deposited bytes/digest; keep a software/source deposit separate if both products need distinct citation identities.
- Paper linkage: https://raw.githubusercontent.com/zenodo/developers.zenodo.org/master/source/includes/resources/deposit/_representation.md — `related_identifiers`: “Persistent identifiers of related publications and datasets.” Its supported list includes “arXiv”; relation vocabulary includes “`isDescribedBy`” and “`isSupplementTo`”. Recommendation: KB record `isDescribedBy` the arXiv paper; paper cites the exact KB version DOI. Actual endpoint/UI submission not tested.
- CFF: https://raw.githubusercontent.com/citation-file-format/citation-file-format/main/schema-guide.md — `preferred-citation`: “A reference to another work that should be cited instead of the software or dataset itself.” Recommendation: do not use that field merely to link a companion paper when direct KB citation is wanted; use references/related identifiers instead.
- Zenodo precedence: https://help.zenodo.org/docs/github/describe-software/citation-file/ — “If your repository also contains a `.zenodo.json` file, Zenodo will **only** use the `.zenodo.json` metadata and ignore the `CITATION.cff` entirely.” https://help.zenodo.org/docs/github/describe-software/zenodo-json/ supplies a `related_identifiers` example with “`"relation": "isSupplementTo"`”.

### V6 — observed CDC axes, without reverse-engineering a policy

https://fhir.org/guides/cdc/opioid-cds/history.html — publication table columns “Date”, “IG Version”, “FHIR Version”; release row `2022.1.1`, `4.0.1`. Description: “Release publication of the 2022 CDC Clinical Practice Guideline for Prescribing Opioids Implementation Guide, version 2022.1.1 (Technical Correction).” Earlier archive link label: “Versions before Technical Corrections: 2022.1.0”. Thus **source edition and computable-artifact revision are demonstrably separate**. No general CDC rule for incrementing the `2022` component found in homepage/history.

CDS Connect scope limit: AHRQ project page and a web search of its artifact/version history. Page reports repository offline; linked annual reports were located, not exhaustively reviewed. No claim that CDS Connect lacks a versioning policy.

### V7 — exact snapshots scale independently of release-name style

- OBO: https://obofoundry.org/principles/fp-004-versioning.html — “Consumers of ontologies must be able to specify exactly which ontology files they used to encode their data or build their applications, and be able to retrieve unaltered copies of those files in perpetuity.” / “Version identifiers MUST either be of the form “YYYY-MM-DD” (that is, a date) OR use a numbering system”.
- OWL: https://www.w3.org/TR/owl2-syntax/#Ontology_IRI_and_Version_IRI — “If an ontology has both an ontology IRI and a version IRI, then a different ontology with the same ontology IRI and the same version IRI should not exist.” This is a convention, not globally enforced: “This specification provides no mechanism for enforcing these constraints across the entire Web”.
- SNOMED: https://docs.snomed.org/snomed-ct-practical-guides/snomed-ct-terminology-services-guide/5-service-implementation-considerations/5.2-enabling-access-to-editions-and-versions — “The `{moduleId}` is an SCTID that identifies the edition.” / “The `{versionDate}` is the effectiveTime of the set of module dependency reference set rows for this version of this edition.” No numeric SemVer assumption follows. LOINC not sampled; OBO + OWL + SNOMED suffice to establish heterogeneous identifier styles.

### V8 — concrete alternatives; all hypothetical, not adopted project law

Common baseline: released bytes immutable; current `g<head12>` filename may remain, but full commit + payload/archive digests identify exact bytes; release record adds a human release ID and version DOI. Source guideline edition stays a separate field. Keep one collection manifest now, with member guideline source edition/content digest; introduce independent guideline release IDs when independently released guidelines need them (V2, V5–V7).

| option | release identifier | meaning of schema `1` after publication | provenance fields beyond common §V4 baseline | tradeoff |
|---|---|---|---|---|
| **A — minimal frozen-schema revisions** | `kb/cdc-2022/v1.0.0`; KB MAJOR for incompatible interface or substantive clinical behavior, MINOR for compatible additions, PATCH for nonsubstantive fixes (V1) | Exact immutable schema + semantics revision. Any contract change, additive included, creates schema `2`; releases name one exact revision. | `kb_version`, `schema_id`, schema digest, source edition, predecessor, clinical-change class | Small policy + no new schema version type. Coarse revision numbering says little about compatibility; composition across revisions needs explicit migration/adapters or a compatibility ruling. No historical artifact rewrite (V2, V7). |
| **B — two-axis SemVer (recommended for corpus growth)** | `kb/cdc-2022/v1.0.0`; independent `schema/1.0.0`; aggregate release manifests pin member versions/digests (V1–V2) | `schema_id=1` becomes compatibility major; add exact `schema_version=1.0.0`. Existing predicate meaning stable within major; additive features earn MINOR only under a defined consumer compatibility contract. Breaking syntax/semantics creates major `2`. | `kb_version`, exact `schema_version` + digest, supported/required schema capabilities, per-guideline content/source identities, compiler commit, predecessor, clinical-change class | Scales additive schema evolution without equating schema changes to content updates. Requires explicit compatibility definition/tests; same major alone must not promise an old consumer understands newly added predicates. Material clinical changes can bump KB MAJOR while schema stays `1.x` (V1, V3). |
| **C — dated immutable KB snapshots** | e.g. `kb/2026-10-22` (example only); deterministic sequence suffix if multiple releases on one day | Exact immutable schema revision, as A; alternatively pair dated snapshots with B's independently versioned schema | `release_date`, snapshot ID, exact schema revision, explicit `schema_change` + `clinical_change` classifications, previous snapshot DOI | Natural for evolving knowledge; no awkward implication that new/corrected facts preserve all old answers (V7). Date gives no compatibility signal; consumers must inspect the manifest/change classes (V3). |

Why B: the product contract is the exported Prolog schema, while the scientific/clinical artifact is the guideline KB. Their revisions are demonstrably separate concerns in FHIR/CQL, and source-edition identity is separate again in CDC (V2, V6). A is the smallest first-publication policy if compatibility tooling is not yet worth building. C is an honest alternative if semantic severity classification becomes noisy; it still needs explicit schema compatibility. No source reviewed establishes that versioning alone makes mixed-schema composition sound.
