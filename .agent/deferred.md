# Deferral queue

Off-path improvements + ruled deferrals, one row each: `- <what> (<source>). Accept: <check>`. A row enters while its evidence is fresh and leaves in the commit that meets its check; a skipped, xfailed, deleted or tier-demoted case enters here with user approval (`CLAUDE.md` `Engineering`). Unfinished units stay in `.agent/spec.md` `Tasks`.

- Kani engine + trace harnesses (`rust/ckc-kani-harness` `engine_answer_tiny`, `reader_trace_check_small`; outside the `just kani` recipe) — waits on its re-open trigger (user ruling). Root cause: Kani lays every `Vec` buffer out as an untyped heap byte object, and CBMC folds a value read back from it only for scalars + padding-free aggregates ⇒ every read of the kernel's unequal-variant enums in heap `Vec`s (term arena `Vec<ENode>`/`ENodeKind`, goal stack `Vec<EGoal>`, clause bodies `Vec<EBodyItem>`) stays symbolic on concrete input ⇒ each engine step branches over every node kind + every data-dependent loop unwinds to its bound; the parser + the engine algorithm are not the cause. Measured: one concrete `unify` f(a)=f(X) rc 124 at 600 s (BTree collections as shipped; again with Vec stand-ins); a loop counted by an arena field (var key, node tag, `maximum`) unwinds to the bound 7 where `Vec<usize>`/`Vec<Option<usize>>` controls unwind exactly 1–3; whole-file `v1_answer` 5 runs rc 124 at 1200 s / ~12 GiB; typed below-parser seam 2-fact answer rc 124 (symbolic 1500 s, concrete 900 s). Re-open trigger: a `rust/kani.lock` bump → rerun `engine_answer_tiny` (cap 1200 s); fund the unit only if that run finishes. Accept: typed below-parser kernel seam + one engine harness and one trace harness green in `just kani`.
