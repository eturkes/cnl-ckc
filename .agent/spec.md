# cnl-ckc spec

## Intent

cnl-ckc compiles the natural language of published clinical guidelines into an executable knowledge base, through a layer that clinicians can audit. Each guideline passage becomes an Attempto Controlled English (ACE) document. Clinicians review each ACE document beside its source passage. The compiler turns each ACE document into plain Prolog that is portable across Prolog engines. This Prolog follows the schema that `docs/REFERENCE.md` specifies. The compiled output includes proof obligations, custody digests and committed demonstration queries. Each query carries its answers and proof traces. The project has three goals, in priority order:

1. An executable knowledge base that software can query and combine. A clinical decision support (CDS) system can later load the knowledge bases of several guidelines together. It can match them against the information of one patient, also when the patient has more than one condition, and give a clinician a recommended course of action. The knowledge base must therefore keep what this matching needs: the conditions of each recommendation, its timing and severity, the strength of each recommendation and the preference of one option over another. The project does not build the CDS system.

2. Clinician-auditable compilation. The project keeps the ACE and Prolog approach. A coverage plan (`docs/m7-gap-taxonomy.md`) tracks the semantic gaps of this approach. The plan records each gap class as covered or open. Example classes are timing, dosing arithmetic, probability and preference strength. Each class is its own piece of work. The compiler is not fixed. Extensions of ACE constructs, further schema revisions and companion or alternative targets stay open for evaluation. One such target is ProbLog, for content that carries uncertainty. Before the knowledge base is distributed, clinicians use the reviewer interface to check that each ACE document is faithful to its source passage. This audit must be as easy as possible for them. This fidelity stays permanently outside formal verification. The knowledge base is distributed only as the tagged full release: unreviewed release candidates and the public repository are pre-release material.

3. Formal verification of the compilation and of every other logical step that the software's function depends on. The verification follows the verified-kernel pattern. A small formal specification is the part that humans read. AI writes the implementation and its proofs, and no human inspects either. A pinned deterministic checker and an escape-hatch audit complete the pattern. The layer that humans must audit stays as small as possible. Soundness for software as a medical device (SaMD) sets the boundary between verified steps and trusted software. Verification covers the logical steps from ACE to clauses to answers. It also covers the custody chain that binds the source, the ACE, the clauses, the review verdicts and the export. Git, the filesystem, subprocesses, the clock, pinned mature dependencies and process or legal validators are trusted software. Fixture gates check this trusted software. Among the verified steps, the Prolog stack keeps one role: emission from ACE through the discourse representation structure (DRS) to clauses. This role keeps verification that humans can review. SWI-Prolog can also propose which statements of the knowledge base hold for one patient, but only as an untrusted producer. The verified Rust kernel alone decides which answers are accepted. Translation validation certifies every compiled document and question against the formal specification.

The scope stays minimal: fetch, normalize to ACE, compile, review locally and export deterministically. The project has no serving layer and uses no large language model at run time. Everything that a human must read is ACE, the formal specification or a named small Prolog closure. The closure stays on this list until it is certified.
